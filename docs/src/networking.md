# Networking & SSH

## The mesh and publishing

- Hosts meet on a **NetBird mesh** (`<host>.nb.lvdar.nl`); the control plane is self-hosted on gaia.
- **Mesh ACL** (gaia's `cosmos.services.netbird.mesh`, `enforce = true`): NetBird's All → All policy is disabled. `nix-fleet` (every den host) reaches itself freely; every peer gets udp/tcp 53 to `nix-resolvers`; `mesh.operators` (panther, the phone) reach the fleet on any port, one way. Any other peer resolves mesh names but cannot connect to them, so "resolves but times out" from a device means it is missing from these lists, not a DNS problem.
- An app aspect becomes public by emitting a `netbird-service = {host, ...}: { <name> = {...}; }` entry (same shape as `cosmos.services.netbird.services.<name>`). gaia's netbird server collects them (`pipe.collect`, x86_64 only) into `cosmos.services.netbird.services`; the producer also appends its port to `cosmos.services.netbird.client.exposedPorts`. Entries are gated behind a NetBird identity check unless `bearerAuth.enable = false` (open because the app runs its own login). Gated: `suwayomi`, `sabnzbd`, `prowlarr`, `radarr`, `sonarr`, `lidarr`, `bazarr`, `lingarr`, `minecraft-control`. The reasoning for each entry sits next to it in the app's aspect — read it before changing gating.
- `cosmos.services.netbird.localVhosts` (gaia) is the escape hatch for domains netbird-proxy *cannot* carry: management rejects any domain that is not a label beneath the proxy's `baseDomain`, so the apex `lvdar.nl` 422s and is served by gaia's own nginx over the mesh instead. Side effect when debugging: the apex keeps working when the proxy does not.
- gaia's nginx (control plane, `oidc.idp`, `localVhosts`) uses its own `netbird-edge` cert naming only those domains, never the `*.lvdar.nl` wildcard. Both sit behind one IP, and with the wildcard, browsers reuse an `auth.lvdar.nl` HTTP/2 connection for proxy domains like `jellyfin.lvdar.nl` and get a 421 Misdirected Request, which not every client retries.
- `cosmos.networking.edgeTerminated`: endeavour = `true` (gaia terminates TLS and forwards to each app's own port, so apps must bind `0.0.0.0` and local nginx vhosts are dropped), gaia = `false` (it *is* the edge). A new service answering locally but not publicly is almost always a missing bind/`edgeTerminated` issue.
- Smoke check when debugging publishing/ingress: `curl -I` against the public name (probes DNS → edge TLS → netbird-proxy → app).

## SSH

Set by `core.ssh` (`modules/den/aspects/core/ssh.nix`) on every host.

- **Port 2222 only.** NetBird's SSH server owns `<mesh-ip>:22` (it answers with a misleading "Permission denied (password)"), so OpenSSH listens on :2222 everywhere; `home.ssh` sets `Port 2222` for `*.nb.lvdar.nl` and the bare server names. Public :22 on gaia is not OpenSSH: it is a kernel DNAT to knot2's own in-process SSH listener on `endeavour:2223`, so no sshd is reachable from the internet except gaia's own :2222.
- **voyager is mesh-only**: `openFirewall = false`, and :2222 is opened on the NetBird interface alone (`cosmos.services.netbird.client.exposedPorts`). A laptop joins foreign networks.
- **Authorized keys** for root and the primary user are exactly the files listed in `modules/den/aspects/core/_ssh-keys/authorized.nix`: `id_voyager` (the workstation's device key), two YubiKey FIDO2 resident keys, and `panther` (the phone's hardware-backed key, [below](#the-phone-panther)). sshd reads only `/etc/ssh/authorized_keys.d` (`authorizedKeysInHomedir = false`), so a hand-placed `~/.ssh/authorized_keys` grants nothing. The installer ISO authorizes the same list. `PermitRootLogin prohibit-password`, no passwords, no keyboard-interactive. Servers hold no user identities, and agent forwarding is off.
- **Break-glass** when voyager's key is lost or rotated wrong: on any machine with OpenSSH, plug in a YubiKey and recover its handle with `ssh-keygen -K` (writes `id_ed25519_sk_rk_lvdar`), then `ssh -o IdentitiesOnly=yes -i id_ed25519_sk_rk_lvdar -p 2222 root@<host>.nb.lvdar.nl`. gaia is also reachable on `lvdar.nl:2222` when the mesh is down.
- **Host keys are pinned**, not trusted on first use: `programs.ssh.knownHosts` is built from each host's `sshHostKey` fact ([Hosts](hosts.md#host-facts)) for its name, deploy address and mesh address (each also as `[…]:2222`). `knot.lvdar.nl` is pinned separately to the knot's own host key (a literal in core.ssh): knot2 does not share endeavour's host key, which is also endeavour's sops identity.
- **Git SSH is the knot's, not sshd's.** knot2 authorizes pushes from users' `org.tangled.key.sshKey` records on their PDS (the format tangled.org writes since its data-format migration), read live with an hour's cache; there is no `git` unix account and no `AuthorizedKeysCommand`.

## The phone (panther)

panther is a GrapheneOS Pixel with the NetBird app, plus Termux and Termux:API, both from F-Droid. The Google Play Termux build cannot run `tergent`, and plugins from a different source than Termux itself cannot talk to it. It is a mesh operator (see above): it can open connections into the fleet, but nothing on the fleet can connect to it.

- **Key:** `panther.pub` in `_ssh-keys/authorized.nix` is an ECDSA P-256 key generated by `termux-keystore` in the Pixel's TEE (not StrongBox: `termux-keystore` never asks for it). It cannot be exported, and the hardware refuses to sign more than 15 minutes after the last unlock (`-u 900`). When `ssh` fails with `Permission denied (publickey)` after a long idle stretch, lock and unlock the phone. The key dies with the Termux apps, and with any change to the lock screen or enrolled fingerprints.
- **Client:** `~/.ssh/config` loads `tergent` as a `PKCS11Provider`, and it signs through Termux:API. The config must not set `IdentitiesOnly`, which drops PKCS#11 keys.
- **Setup / refresh** (after a host key rotation or a host change): `nix build .#termux-ssh`, copy `result/` to the phone, then run `sh install.sh` from it in Termux. The bundle holds an `~/.ssh/config` with `ssh <host>` shorthands (mesh name, :2222, the right user) and `known_hosts.fleet`, pinned from the `sshHostKey` facts. The script creates the `panther` key if it is missing and prints the public key. A new key also means replacing `panther.pub` and deploying every host.
- **Managing from the phone:** `ssh endeavour` (or any host) from Termux, with `tmux` on the far side so a dropped mobile connection does not kill the session. To deploy, `ssh voyager` and run `deploy` there: deploy-rs keeps running from voyager, and the phone holds no deploy credential of its own. In the browser, use the published UIs: the NetBird dashboard (panther's user is in `netbird-admin`), grafana, and the gated *arr apps.

## Coding agents on endeavour

`services.coding-agents` (included on endeavour) adds an `agent` user that runs omp, with the same pinned build and settings as voyager.

- **Unprivileged on purpose.** `nixos` has passwordless sudo, and endeavour's host key is its sops identity, so an agent running as `nixos` would be root over every secret on the box. `agent` has no wheel and no service groups, and is not a nix trusted user. It can build with nix and edit its own home, and holds no deploy, push or sops credential. Anything that has to leave the box goes through you: it commits as `agent@endeavour <agent@endeavour.nb.lvdar.nl>`, and you fetch from `ssh://agent@endeavour:2222/home/agent/dev/<repo>`.
- **AppArmor `agent-session`.** Login runs a private copy of bash (`agent-shell`), so sshd-session transitions it into the `agent-session` profile, and everything it starts inherits that profile. Its `deny` rules hold even in complain mode: no setuid wrappers, user namespaces, capabilities, `/var/lib`, `/tank`, secrets, other homes, the user systemd bus, or systemd/environment.d units in `~` ([AppArmor](apparmor.md)).
- **Egress.** An iptables `agent-egress` chain on the `agent` uid's OUTPUT allows replies on established connections (sshd, mosh), host DNS, and loopback TCP 20000–20999 (dev servers) plus 32768–60999 (omp's Python eval bridge binds an ephemeral port; a service on a random port there stays reachable). It rejects every other local address, the LAN, the NetBird mesh (100.64/10), docker/podman networks, link-local and multicast. The public internet stays open.
- **Per-clone sandbox.** The agent's `omp` is a wrapper that only starts inside `~/dev/<repo>` and runs omp under Landlock via a private landrun copy (`omp-landrun`, `--best-effort` because endeavour's kernel has Landlock ABI v7). It can write only that clone, `~/.omp` (login, sessions), `/tmp`, `/var/tmp`, and a per-clone `HOME` in `~/.cache/omp-sandbox/<repo>` that links `~/.omp` and `~/.config`; other clones and the real home are unreadable. ABI v7 doesn't mediate `connect()` on path sockets, so `agent-session` transitions `omp-landrun` into the AppArmor child profile `agent-sandbox`, which denies the tmux sockets. That deny is plain `deny`, so it holds in complain mode but logs nothing (`audit deny` would be downgraded to allow+log there). `omp-unsandboxed` skips Landlock and stays under `agent-session` and the egress chain. `~/.omp/agent/AGENTS.md` tells omp these limits.
- **Login:** the keys in `_ssh-keys/authorized.nix`, directly as `agent` (no sudo hop). Every interactive SSH or mosh login execs `tmux new-session -A -s agent`, so reconnecting resumes the running session. omp's login (`/login`) and `~/dev` persist across reboots.
- **From the phone:** `mosh agent` (or `ssh agent`) in Termux; the bundle's `Host agent` points at endeavour as `agent`. mosh survives network switches and the phone sleeping. Its UDP 60001–60010 is open on the NetBird interface only, which caps it at ten concurrent sessions; a server whose client disappeared exits after a day (`MOSH_SERVER_NETWORK_TMOUT`, set by sshd for `agent`).
